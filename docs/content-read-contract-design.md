# 內容讀取契約與隱藏區塊（設計草稿）

狀態：**草稿。** 2026-10-12 審閱：方向（設計原則）獲認可，但尚未授權實作；§3、§4、§5 的具體決定仍要逐項核准才生效，隱藏能力的實作要等 §4.5 舊 build 政策定案。
所述「現況」已於 2026-10-12 對照 `main`（`02024d9`）核對；2026-10-16 依已合併的 #224、#246 對照 `main`（`468a9f4`）重新核對，新增 §2.0，並更正 §2.1、§2.2、§3.2 已過時的描述。§2.3 的實驗表是 2026-10-10 在 `149d185` 上做的，之後沒有重跑。§2.4 是 2026-10-13 在 `82b0bc6` 上的初步實驗紀錄，結論只限該次實作與已測案例；記錄它不代表核准任何新設計或實作。

**範圍。** 本文件只定義**讀取與隱藏**：Theme 讀內容時各種區塊狀態要回傳什麼，以及「隱藏」怎麼在不限制作者寫法的前提下成立。它**不是**完整的綁定契約。Design 如何確認畫面元素屬於哪個頁面、區塊實例、重複列與欄位，另見綁定契約草稿（`docs/content-binding-contract-design.md`，獨立 PR）。本文件核准，不代表綁定相關工作都可以開始；本文附錄的實驗是那份契約的證據，不是這份的一部分。

## 1. 目標與非目標

目標：

- 作者用框架原本的寫法讀內容，包括逐欄傳值 `<Hero title={hero.title} />`，不必為了 Morph 改寫程式。
- 編輯器裡的「隱藏」在正式網站真的不顯示，且不讓頁面崩潰。
- 被隱藏的內容不出現在目前 release 的公開回應中。
- **最終目標（不變）**：隱藏 = 預覽和發布結果都看不到；作者程式不必加任何 Morph 專用的判斷；頁面不會因此壞掉。只讓讀取回傳 `{}` 不算完成（§3.2、§4.7）。

非目標：

- 不保證收回曾經公開過的內容（舊 release、快取、已被下載的頁面）。
- 不保護作者直接寫進原始碼、JS、HTML 或靜態資源的資料。隱藏不是保密功能。
- 不保證任意寫法**現在**就能自動隱藏。目前無法安全處理的區塊實例，暫不開放隱藏；這是能力限制，不是對作者寫法的要求（§4.2）。
- 不定義跨框架綁定（見上方「範圍」）。

## 2. 現況

### 2.0 2026-10-16 更新：#224、#246 合併後的事實（main `468a9f4`）

以下都是已合併的程式，不是提案。

- **#224（隱藏選取，main `6779d01`）只處理編輯器，不改渲染。**
  - 隱藏區塊在畫布、Sections 面板與網址都不能被選取，Inspector 不提供內容編輯，也不送出寫入 Document 的樣式修改（`visual-editor-shell.tsx`、`editor-assistant-panel.tsx`、`editor-style-inspector.tsx`）。
  - 預覽編譯時，loader 取得的區塊若列在該頁的 `_hidden`，外層會加上 `data-morph-section-hidden`（`inject-preview-bindings.ts` 的 `SECTION_HIDDEN_ATTRIBUTE`；`preview-dom.ts` 的 `PREVIEW_SECTION_HIDDEN_ATTRIBUTE`、`isInHiddenPreviewSection`）。
  - **這個標記不改變畫面**：程式註解寫明區塊內渲染的是元件預設值，標記只讓編輯器不提供選取。也就是說，預覽中被隱藏的區塊**仍然看得到**（以預設值顯示），§1 的最終目標沒有因 #224 達成。
  - 沒有改伺服器、OCC、發布或內容契約。
- **#246（SDK 讀取核心 v0，main `468a9f4`）新增一個平台擁有的讀取核心**，位置在 `packages/morph-sdk/`。
  - `pages.get` 回傳的形狀與 Starter 的 `morph.pages.get()` 相同：slot 攤平在頁面物件上，隱藏區塊**不在**頁面物件上（`page.hero` 是 `undefined`），id 列在 `_hidden`（`packages/morph-sdk/src/client.ts` 的 `readPage`）。形狀的單一定義在 #245 `docs/morph-sdk-read-contract.md` §6.0、§6.2，本文引用，不另寫一份。
  - 它只在伺服器端讀，沒有接進 app、Starter 或任何 Theme；託管 Theme 仍用 Starter 自己的 `src/morph/content.ts`。
  - 因為形狀相同，§2.3 表中「被隱藏 → 逐欄存取整頁崩潰」同樣適用於 SDK v0 的回傳值。【推論，未執行】：SDK v0 沒有在 React 渲染中實測過這一列。

### 2.1 兩層：Core 的公開回應與作者端讀取

內容經過兩層，兩層的形狀不同，本文件的每一條規則都會指明是哪一層：

| 層 | 誰的程式 | 隱藏區塊的樣子 |
|---|---|---|
| **Core 公開回應**：`/_morph/content`（`storefront-production.service.ts` `serveContent` → `resolveStorefrontContent`） | 平台 | 從 `slots` 移除，id 列在 `hiddenSlots`；**不含原始內容** |
| **作者端讀取**：Theme 的 `src/morph/content.ts`（Starter 提供初版，之後屬於作者，規則 01 §4.4） | 作者 | `content(id)` 回 `slots[id] ?? {}`；`isSectionHidden(id)` 讀 `hiddenSlots`；`morph.pages.get(path)` 回 `{ ...slots, _hidden: hiddenSlots }`，所以隱藏區塊在 `page.hero` 是 `undefined` |
| **SDK 讀取核心 v0**：`packages/morph-sdk/`（#246，2026-10-16 新增） | 平台 | `pages.get(path)` 與 Starter 的 `morph.pages.get()` 同形：隱藏區塊在 `page.hero` 是 `undefined`，id 在 `_hidden`。目前沒有任何 Theme 使用它 |

其他已核對的事實：

- Core 的 `/_morph/content` 對合法的路徑一律回 200 與 `resolveStorefrontContent` 的結果；沒有 Document 時是 `{ slots: {}, hiddenSlots: [] }`（有 layout 文件時只含 layout 的內容）。內容端點本身只在方法不對（405）、路徑不合法（400）或未設定內容來源（503）時回錯誤。
- **更正 2026-10-12 稿（漏列）**：在進入內容端點之前，Core 先依網域解析商店與 release；網域、商店、release 或 build 不成立時回純文字 400／404／503（詳見 #245 §3.1）。因此 Starter 的 `MorphContentError("content_not_found")` 在正式環境代表「這個網域沒有可讀的已發布商店」，不是「這頁不存在」；SDK v0 沿用同一個碼與同一個語意（#245 §6.0）。`docs/local-development.md`「讀不到時顯示明確的原因」對正式環境仍不成立。
- 預覽快照（`createThemePreviewContentSnapshot`）呼叫同一個 `resolveStorefrontContent`；預覽的即時隱藏（`theme-preview-content.ts` `updatePreviewContent`，`enabled === false`）是另一段程式，同樣移除該區塊。
- 「恢復元件預設值」已存在：寫入時的 `resetProps`，Inspector 的「重設為程式碼預設值」。
- 更正 2026-10-10 稿：當時寫「`content("x")` 經 `resolveThemeContentSlot` 回 `{}`」。`resolveThemeContentSlot` 只有相容性直譯器使用；作者的 `content()` 自己回 `?? {}`，結果相同，但這是作者檔案的行為，不是平台保證。

### 2.2 已修好與仍未支援

- **已修好（#208，Starter 29）**：Starter 的 layout 與首頁路由在渲染前問 `isSectionHidden`，隱藏的 Header、Footer 與首頁區塊在重新載入與正式網站都不顯示。這只涵蓋 Starter 自己的寫法，以及升級時位元組未改的舊檔案。
- **已修好（#224，編輯器端）**：隱藏區塊不能被選取，也不接受 Inspector 的內容與 Document 寫入（§2.0）。這是編輯器的保護，**不是**渲染上的隱藏。
- **仍未支援（2026-10-16 依 main `468a9f4` 核對，未改變）**：作者用 `morph.pages.get()` 解構、loader → `useLoaderData()` 等原生資料流，而沒有自己判斷隱藏時，隱藏區塊是 `undefined`，逐欄存取會讓整頁崩潰；只展開（`{...page.hero}`）時則顯示元件預設值。#224 與 #246 都沒有改變這一點。§3、§4 處理的就是這一類。

平台的 `resolveStorefrontContent` 組內容 → 原封不動的 Starter `morph.pages.get()` → 真 React 渲染逐欄傳值、不加 `?.` 的元件。實驗測試尚未納入 repo，待改寫為有明確斷言、可重跑的正式測試後另行提交。

| ---------------------------------------- | ------------------------ | ----------------------------------------------- |

### 2.4 實驗（2026-10-13，`exp/hidden-rendering`，初步報告）

**結論的範圍。** 本節所有發現只適用於**本次實驗的實作**（各方案在 `exp/hidden-rendering` 裡的寫法）與**已實測的案例**（下表 7 種 Start 寫法、`.astro` 的辨識案例）。不推及同一方案的其他實作方式、其他作者寫法，或下方「未驗證」所列的層級。

**版本與範圍**

- 實驗分支 `exp/hidden-rendering`，基於 main `82b0bc6`，只有本機 commit：`99ae52e`、`e4a7d20`、`fa35029`、`60ae700`，沒有推送。
- 實驗程式只放在 `src/lib/storefront/experiments/hidden-rendering/`，另外複製了 #221 的 fixture；沒有修改產品程式碼。曾有一次對 `storefront-content-runtime.ts` 的嘗試修改，已立即還原，之後核對 blob 與 main 相同。
- 驗收目標（使用者訂定）：預覽不顯示；發布結果不顯示；作者不需要寫 Morph 專用的判斷；正常計算不崩潰。只回傳 `{}` 不算完成。

**比較的方案（本次實作）**

- **現況（baseline）**：被隱藏的 slot 不出現在 payload，原始碼照作者寫的執行。
- **A-html（輸出時移除）**：payload **帶被隱藏 slot 的儲存值**（模擬改變 `resolveStorefrontContent` 的輸出），並列在 `hiddenSlots`；元件照常渲染，再從伺服器 HTML 移除該區塊。A-html 沿用 `injectPreviewBindings` 的辨識範圍，A-html-ext 用擴大後的範圍。
- **A-wrap**：與 A-html 相同的 payload（帶儲存值），改在呼叫點包一層 `<__MorphHide when={hidden}>`：props 照算，元件不執行。
- **B（編譯時注入）**：payload 維持現況，把可辨識的呼叫點改寫成 `{hidden ? null : <El/>}`。B-core 只涵蓋綁定分析的範圍，B-ext 額外涵蓋呼叫點計算。

**已實測：Start／React，在同一個程序內跑 SSR 與 client hydration**

環境：jsdom、真實的 React 19 `renderToString` 與 `hydrateRoot`、兩個真實的 TanStack router、真實的 Starter `src/morph/content.ts`。server function 在同一個程序內執行，沒有 Start 的 dehydration。證據：實驗分支的 `hidden-rendering.start.live.test.ts`「measures the matrix」。

| 寫法                                      | 可見時     | 現況       | A-html                         | A-html-ext       | A-wrap | B-core     | B-ext    |
| ----------------------------------------- | ---------- | ---------- | ------------------------------ | ---------------- | ------ | ---------- | -------- |
| `<Hero {...content("hero")}/>`            | 顯示儲存值 | 顯示預設值 | 不一致後重新出現               | 同左             | 不顯示 | 不顯示     | 不顯示   |
| 呼叫點計算 `content("hero").title.toUpperCase()` | 顯示儲存值 | **崩潰**   | 顯示儲存值                     | 不一致後重新出現 | 不顯示 | **崩潰**   | 不顯示   |
| loader 解構後展開                         | 顯示儲存值 | 顯示預設值 | 不一致後重新出現               | 同左             | 不顯示 | 不顯示     | 不顯示   |
| loader 整頁物件 `{...home.hero}`          | 顯示儲存值 | 顯示預設值 | 不一致後重新出現               | 同左             | 不顯示 | 不顯示     | 不顯示   |
| loader 呼叫點計算                         | 顯示儲存值 | **崩潰**   | 顯示儲存值                     | 不一致後重新出現 | 不顯示 | **崩潰**   | 不顯示   |
| loader 在 JSX 之前提前計算                | 顯示儲存值 | **崩潰**   | 顯示儲存值                     | 不一致後重新出現 | 不顯示 | **崩潰**   | **崩潰** |
| 同一個 slot 展開兩次                      | 顯示儲存值 | 顯示預設值 | 顯示儲存值                     | 不一致後重新出現 | 不顯示 | 顯示預設值 | 不顯示   |

「不一致後重新出現」：React 回報可恢復的 hydration 錯誤，client 重建後，被隱藏的區塊帶著儲存值又出現。「顯示儲存值」在 A 系列的欄位裡，表示被隱藏的區塊照樣顯示。

**已實測：`.astro` 只做辨識，沒有渲染**（實驗分支的 `astro-hidden-guards.test.ts`）

- 每個變體的輸出都能重新解析，沒有診斷訊息；含非 ASCII 字元的原始碼，位移正確。
- 核心範圍涵蓋 `{...home.hero}` 與 `const {hero}=home; {...hero}`；模板裡的呼叫點計算需要擴大的範圍。
- frontmatter 裡的提前計算，在所有方案下都標為「無法防護」。
- `const {hero: about} = await morph.pages.get(...)` 兩種範圍都辨識不到。

**目前的發現（限本次實作與已測案例，不是決定）**

1. **A-html 與 A-wrap 都和 §3.1 衝突**：本次兩者的 payload 都把被隱藏區塊的儲存值放進公開的 `/_morph/content` 回應（固定快照也是同一份輸出），違反「公開回應不帶隱藏內容」。實驗矩陣的 `payloadCarriesHiddenValues` 對 A-html、A-html-ext、A-wrap 都是 `true`，對現況與 B 都是 `false`。A-wrap 已由使用者 2026-10-13 決定不列入可採用方案；A-html 的取捨沒有另外決定，但同樣不符合 §3.1。
2. **本次的 A-html 在已測的 Start 寫法下不滿足驗收第 1、2 項**：從 HTML 移除的區塊造成 hydration 不一致，client 端帶著儲存值重新出現。沒有 island 的 Astro 頁面結果可能不同，但**沒有量**。
3. **本次的 B 沒有改變 payload**，已測寫法的 hydration 一致；但在 JSX 之前的計算仍會崩潰（B-core 另有呼叫點計算崩潰），與 §4.2 的判斷一致。本次的 B 依賴作者擁有的 SDK 檔案裡的 `_hidden`／`isSectionHidden`；作者改過那個檔案時，可能失去保護（未測）。
4. **在已測的 7 種 Start 寫法中**，本次實作的變體只有 A-wrap 同時不崩潰、不顯示、hydration 一致；這個結果不能脫離它對 §3.1 的違反單獨引用。
5. 「能辨識就用 B、其餘用 A-html」在已測的 Start 寫法下不成立，原因見第 1、2 點。
6. **建置上的需求（依本次實作推論，未實作）**：B 的 TSX 部分可以延伸現有的 `prepareSourcesForBuild`；`.astro` 需要新增檔案語言處理步驟，main 上沒有。A 系列需要在發布建置輸出區塊標記、SSR 回應加處理步驟、預先渲染的 HTML 要後處理。

**未驗證**（重型執行被權限檢查擋下，沒有繞過，依使用者決定停在初步報告）：Astro 預覽的 SSR（astro dev）；完整 Start 預覽的 SSR，包括被隱藏的文字會不會進到 dehydrated `<script>` 資料；兩種框架的固定快照預先渲染建置；經由建置後 Worker 的發布 SSR；A-wrap 在固定建置裡的情況；真瀏覽器的 hydration；Astro islands；實驗分支本身的 typecheck、test、build。

## 3. 契約（待核准）

### 3.1 Core 公開回應：不變

- 隱藏區塊仍**不出現在** `slots`，只以 id 列在 `hiddenSlots`。公開回應不帶隱藏內容，也不為它補空物件。
- 正式網站、預覽快照、預覽即時隱藏三條路徑維持同一種回應形狀（§4.6），不各自改成不同形狀。
- **已知衝突（2026-10-13 實驗，§2.4）**：本次實作的 A-html、A-html-ext 與 A-wrap 都需要被隱藏區塊的儲存值出現在公開回應（與固定快照）中，違反本節。本契約不因此改變。在已測的 Start 寫法中，同時滿足「不顯示、不崩潰、hydration 一致」的只有 A-wrap，所以這個衝突不能用「改用 A-html」迴避。§3.2 的 `{}` 只保留一層形狀，仍會顯示預設值，深層存取仍會崩潰，不能單獨滿足驗收目標。

### 3.2 作者端讀取：在 SDK 這一層補形狀

| 情況              | `content(id)` | `morph.pages.get()` 的 `page[id]` | 說明 |
| ----------------- | ------------- | --------------------------------- | ---- |
| 區塊存在但沒內容  | `{}`          | `{}`                              | 維持現狀 |
| **區塊被隱藏**    | `{}`（維持）  | **`{}`，id 仍在 `_hidden`**        | 改變：`page[id]` 從 `undefined` 改為 `{}`；依 `hiddenSlots` 在 SDK 補上，Core 不變 |
| 區塊不存在        | `{}`（維持）  | 不補（`undefined`）               | 維持現狀，不掩蓋寫錯的 slot 名稱 |
| 頁面沒有 Document | 維持現狀      | 維持現狀（空內容）                 | 見 §5，先修文件承諾 |
| 欄位為 `""`       | 保留          | 保留                              | 代表作者刻意清空 |
| 欄位為 `null`     | 依欄位型別契約決定是否允許 | 同左                  | 不做全域轉換 |
| 恢復元件預設值    | 移除該欄位（既有 `resetProps`） | 同左            | 不用 `null` 或 `""` 表示 |

**這一層現在有兩種讀取模組，擁有者不同（2026-10-16 更新）：**

- **Starter 的 `src/morph/content.ts` 是作者的檔案。** 這一層的改變以新的 Starter 版本提供，升級時只替換位元組未改的 `content.ts`（與 #202、#208 相同的升級規則）；作者改過的模組保持原樣，Design 應能說明「這個 Theme 的讀取模組沒有這項行為」。不得改寫作者的模組。
- **SDK 讀取核心（`packages/morph-sdk/`，#246）是平台的程式。** 作者不在 Theme 裡修改它。它的 `pages.get` 形狀由 #245 契約定義（§6.0、§6.2），本表若核准，要改的是 #245 的契約與 SDK，而不是在本文另寫一份形狀。依 #245 §7 的版本規則，`MorphPage` 形狀的改變屬於 breaking，要升 major。
- 兩者必須回傳同一種形狀；任何一方單獨改變，都會讓同一個頁面在兩種讀法下行為不同。

**目前狀態**：上表「區塊被隱藏 → `page[id]` 為 `{}`」**尚未實作**。Starter 與 SDK v0 都仍回 `undefined`（§2.0、§2.1）。

**`{}` 的作用僅限於保留區塊物件的形狀**：`page.hero.title` 會得到 `undefined` 而不是崩潰，但 `page.hero.title.toUpperCase()` 這類依賴值的表達式仍會出錯，而且沒有判斷的頁面會把隱藏的區塊用元件預設值顯示出來。避免執行隱藏區塊的表達式、讓區塊真的不顯示，都由 §4 的判斷負責，不由 `{}` 負責。

## 4. 隱藏：由編譯流程注入判斷（待核准）

### 4.1 原則

- 隱藏內容不出現在公開回應（§3.1）。
- 能安全處理的區塊實例，在正式建置與預覽時自動加入「隱藏就不渲染」的判斷；作者原始碼不變。
- 目前無法安全處理的實例，暫不開放隱藏，並說明是能力限制（§4.2、§4.4）。

### 4.2 判斷必須早於 props 計算

注入結果要像：

```tsx
isHidden(page, "hero") ? null : <Hero title={page.hero.title.toUpperCase()} />;
```

不能先算出 props 再交給包裝元件隱藏，否則 props 的計算仍會先執行而崩潰。

**目前的能力限制：在別處先算好的值。**

```tsx
const title = page.hero.title.toUpperCase();
return <Hero title={title} />;
```

這是普通的框架寫法，不是錯誤寫法。問題在於計算發生在 JSX 之前，在 JSX 處注入判斷救不了。依規則 02 鐵則 6（AST patch 只在能證明安全時進行），目前這類實例**暫不開放隱藏**；作者的程式照常執行、預覽、建置，Code 照常可改。這是 Morph 目前做不到，不是要求作者改寫。

後續支援方向（各自要再設計與驗收，本文件不承諾時程）：

1. **可證明的提前計算**：同一個函式內、只在單一 JSX 使用、沒有副作用的區域常數，transformer 能證明把計算移到判斷之後語意不變時，自動處理。
2. **可選的明確綁定出口**（見綁定契約草稿）：作者標明「這個實例對應 `/home` 的 `hero`」，讓 Design 確認實例與欄位。**它不解決提前計算的崩潰**：出口只告訴 Morph「這是哪個實例」，不會讓已經先執行的 `page.hero.title.toUpperCase()` 不執行。不能把「包一層元件」或「加一個標記」說成隱藏已經完成。
3. 作者自己在程式裡判斷（例如 `morph.pages.isHidden(page, "hero")`）一直可用，但**不是必要條件**，也不是 Morph 對作者的要求。

### 4.3 能力檢查（與權限檢查分開）

既有的登入、角色、所有權與 OCC 檢查不變。新增的是**能力檢查**：這個區塊實例能否安全支援隱藏。

會改變或帶入 `enabled` 的伺服器路徑（2026-10-10 以 grep 初步盤點，實作前須在當時的 main 逐一確認）：

| 路徑                                             | 入口                                                   | 對 `enabled` 的影響                              |
| ------------------------------------------------ | ------------------------------------------------------ | ------------------------------------------------ |
| `storefrontThemeDal.updateSectionProps`          | `updateStorefrontThemeSectionProps`（`props.enabled`） | 直接設定，Design 的隱藏走這裡                    |
| `storefrontPageDal.update`                       | `storefront-pages.serverFn.ts`                         | 寫入整份頁面 Document，`enabled` 由輸入決定      |
| `storefrontPageDal.restoreRevision`              | `storefront-pages.serverFn.ts`                         | 把舊版 Document 還原成草稿，帶回當時的 `enabled` |
| `reorderSections`、`renameSection`、文字升級寫入 | 各自的 server function                                 | 沿用既有區塊物件，理論上不改 `enabled`，需確認   |

不在此表、也不得套用本守衛的路徑：

- `storefrontThemeDal.restoreFailedPublish`：部署失敗時的補償，把 release 指標還原成發布前的狀態，不倒退草稿與 OCC 版本。加上守衛會擋住失敗復原。
- 回滾已發布的 release：恢復的是一組歷史 build 與內容版本，見下方「判斷的對象」。

能力檢查應放在上表路徑共用的 service／DAL 邊界，不只擋單一 server function。

**檢查分兩個階段，規則不同：**

| 階段           | 判斷的對象 | 規則 |
| -------------- | ---------- | ---- |
| **編輯草稿**   | 目前已儲存的 source generation | 改成隱藏（`enabled` 從 true 變 false）時要求能力成立。取消隱藏永遠允許。未改變隱藏狀態的寫入（改文字、重新排序等），不因既有隱藏區塊失去能力而被拒絕，避免作者被鎖住。 |
| **建置與發布** | **該次 build 實際使用的 immutable source revision（`sourceRevisionId`）與它配對的內容快照** | 檢查要發布的整份內容快照裡**所有**隱藏區塊，不只本次改動的。不得拿當下的工作區去判斷另一份 build：作者可能在 build 之後又改了原始碼，兩者不是同一份程式。 |

**判斷的對象永遠是那份 build 與那份內容：**

- **還原 Document 到草稿**（`restoreRevision`）：結果是新的草稿，之後發布時照「建置與發布」階段，用那次 build 的 source revision 檢查。還原本身可以標示「這個版本含有目前程式碼無法安全隱藏的區塊」，但不因此拒絕還原。
- **回滾已發布的 release**：恢復的是當時的 build 與內容版本，能力依那組 build 的 source revision 判斷，不能因為目前工作區的程式已經改變，就拒絕一次合法的回滾。若那組 build 本身不含判斷，依 §4.5 舊 build 政策（待定）處理。

### 4.4 能力失效與恢復出口

已隱藏的區塊，作者之後修改原始碼，使它目前無法安全處理：

- **工作區不鎖住**：草稿仍可儲存、預覽、編輯其他內容。
- **在 Design 明確標示，措辭是能力限制**：例如「這個區塊已隱藏，但 Morph 目前無法保證它在正式網站不顯示（原因：值在渲染前先計算）」。不寫成作者的程式有錯。
- **恢復出口**：
  1. 取消隱藏（永遠允許）；
  2. 原始碼再次變成 Morph 能證明安全的狀態時，能力自動恢復——不指定作者必須改成哪一種寫法；
  3. §4.2 的後續支援到位後，同一份原始碼可能直接恢復能力，不需作者動作。
- **發布**：要發布的內容快照若含有「隱藏但無能力」的區塊，拒絕發布，列出區塊、原因與恢復出口，不得默默顯示。
- **Build Preview**：仍可產生預覽讓作者檢視，但必須帶出同樣的診斷，而且**不宣稱這次建置可發布**，也不把先前成功的預覽當成這次的成功結果。

### 4.5 SSR、SSG 與舊 build

- **SSR**：含判斷的建置產物，依 release 的內容決定是否渲染。隱藏狀態改變屬於內容變更，不需重建。
- **SSG／預先渲染**：HTML 已寫死。隱藏狀態改變時，沿用既有的內容依賴規則（`e2e/native-content-dependency.spec.ts`：只有建置證明不含內容時，內容發布才可跳過建置）決定是否重建。
- **舊 build（政策，使用者 2026-10-12 審閱提出，待隨本文件核准）**：注入判斷之前的建置產物不具備這個能力，不得假定舊 build 已受保護。
  - **新的隱藏變更要發布時**：若要沿用的既有 build 不具備對應能力，要求重新建置；不得用舊 build 發布這次隱藏。Design 在發布前說明「需要重新建置才會生效」。
  - **回滾歷史 release**：恢復的是當時那一組不可變的 build 與內容快照，原樣恢復。不得在回滾時暗中重新建置，仍稱為同一次回滾；需要新能力時，那是一次新的建置與發布，不是回滾。
  - 回滾到不具備能力的 build 時，若那組內容快照含有隱藏區塊，Design 說明那個 release 的實際行為（可能顯示為元件預設值），不宣稱已隱藏。
  - 實作隱藏能力之前，先以這項政策定案。

### 4.6 三條路徑同時修改

正式網站（`resolveStorefrontContent`）、預覽快照（`createThemePreviewContentSnapshot`，共用前者）、預覽即時隱藏（`updatePreviewContent`）要一起改，維持 §3.1 的同一種回應形狀，避免預覽與正式行為不一致。

### 4.7 驗收

每個案例同時檢查：

1. 不崩潰；
2. 真的不顯示（不是改成顯示元件預設值）；
3. 目前 release 的 `/_morph/content` 回應、SSR HTML、預先渲染 HTML 都不含被隱藏的內容；
4. 取消隱藏後重新顯示原本的內容；
5. 修改原始碼使實例失去能力後：Design 以能力限制的措辭提示、工作區可繼續操作、恢復出口都有效、發布被拒絕並列出原因、Build Preview 不標示為可發布；
6. 發布檢查用的是那次 build 的 source revision，不是當下工作區（在 build 之後修改原始碼，不影響那次 build 的判斷）；
7. 還原舊版草稿不被拒絕；回滾已發布的 release 依當時的 build 判斷，不受目前工作區影響；部署失敗補償（`restoreFailedPublish`）不受守衛影響；
8. 作者改過的 `content.ts`：Starter 升級不替換它，行為照作者的模組，Design 能說明。

案例至少涵蓋：`content("x")`、`{...page.x}`、逐欄傳值、值經轉換、先在別處計算值（目前暫不開放，提示為能力限制）、Start 與 `.astro` 頁面，以及每一條 §4.3 的寫入路徑。
