# Design 編輯等級與覆蓋率驗收規格（2026-10-30 使用者同意作為 ROADMAP 1.2 的補充）

本規格補充 ROADMAP 1.2「綁定驗收規範」（2026-10-21 草稿），不取代它。1.2 已確立的規則照舊：讀取不依賴綁定、相同資料流得到相同綁定、以案例集驗收而非語法白名單、共用資料流模型不寫元件特例、安全拒絕不算通過。本規格新增四件事：

1. 每個可編輯的欄位與操作都必須有一個編輯等級，不允許「沒有反應」；
2. 每個等級各自的驗收條件；
3. 以真實程式碼語料衡量覆蓋，不靠逐一想像寫法；
4. 規則擴充與交付的順序。

## 1. 兩份契約，分開驗收

| 契約 | 承諾 | 不承諾 |
|---|---|---|
| 執行契約 | 在支援的框架、依賴與執行環境內，合法程式照常儲存、預覽、建置、發布；存著的 Document 照常讀取、渲染、保留（1.2 第 1 條） | 作者程式本身的錯誤、外部 API 失敗、未核准的依賴 |
| 編輯契約 | 預覽中每個可點選元素上的每個欄位與操作，都有一個明確的編輯等級與對應的編輯入口 | 任意畫面結果都能在畫布上直接改字並自動寫回 |

分類完整（沒有未分類）是編輯契約的前提，不是功能支援的證明。B-partial 與 G 即使已分類，仍是能力缺口；能說「支援」的只有通過第 3 節驗收的 A、A-code，以及來源清單完整的 B。

## 2. 編輯等級

分類的單位是「欄位 × 操作」，不是整個元素。同一個元素可以同時有不同等級，例如標題文字是 A、連結網址是 C、背景圖是 G；同一個欄位的不同操作也可以不同，例如 Inspector 編輯是 A、畫布直接改字因格式限制是 B。操作包括畫布改字、Inspector 編輯、隱藏、排序、刪除等。判定一律依據證據；證據不足就往下降級，不往上猜。

| 等級 | 條件 | Design 的行為 | 寫入目標 |
|---|---|---|---|
| **A 直接寫回** | 已證明值來自唯一一個 CMS 欄位，且可以安全反推（含頁面身分、區塊／列實例、欄位路徑、欄位宣告、來源版本，1.2 契約） | 畫布直接改字、Inspector 編輯 | 該 CMS 欄位（Page／Document） |
| **A-code 程式預設值** | 可證明的元件預設值，呼叫處未傳入該 prop（#290） | Inspector 編輯，標明「改的是程式碼預設值」 | 元件檔案的預設值，經專屬原始碼寫入路徑，不寫 Document |
| **B 來源已知、不可反推** | 已證明值由一個或多個 CMS 欄位組成，但無法唯一反推（例：`firstName + lastName`、經轉換函式） | 不允許畫布直接改字；Inspector 列出每個來源欄位（所屬頁面、實例、欄位路徑），作者直接編輯原始欄位 | 作者選定的原始欄位 |
| **C 由程式碼控制** | 已證明值沒有 CMS 來源（字面值、純程式計算） | 標示「由程式碼控制」，提供跳到原始碼位置（檔案與行）的入口 | 不寫 CMS；只經 Code 模式修改 |
| **G 能力缺口** | 可能有 CMS 來源，但目前的追蹤無法證明是或不是 | 標示「Morph 尚無法判斷這裡的來源」，提供跳到原始碼的入口；不寫入 | 不寫入 |

規則：

- **C 和 G 必須分開。** C 是已證明的結論，G 是 Morph 的能力不足。G 一律計為缺口，不能寫成「由程式碼控制」。
- **B 的來源清單要誠實。** 列出的每個欄位都必須確實參與這個值。若無法證明清單完整，Inspector 要註明「可能還有其他來源」，並計為 B-partial。
- **未分類是缺陷。** 可點選的元素上，有欄位或操作沒有等級，不是缺口，而是錯誤，必須修正。未分類為 0 只表示分類完整，不表示功能支援。
- **降級要留紀錄。** 一個欄位與操作在語料中從較高等級變成較低等級，必須在報告中說明原因；沒有說明就視為回歸。

## 3. 各等級的驗收條件

| 等級 | 驗收 |
|---|---|
| A | 沿用 1.2 的四項：選到正確欄位、Inspector 修改後畫布更新、Document 寫入的是原始值、重新載入後三者一致。另外要有反向案例：同名但不同來源的欄位，不得被寫入 |
| A-code | 只改元件檔案中該預設值；呼叫處一旦傳入同名 prop，就不再是 A-code；伺服器驗證來源版本後才寫入（#290 規則） |
| B | 來源清單中每一項都正確（不含無關欄位）；改其中一項後畫布更新，其他欄位不變；畫布直接改字被拒絕且說明原因 |
| C | 跳轉位置指向產生該值的檔案與行；任何操作都不寫 Document |
| G | 說明文字正確；不寫入；在覆蓋率報告中逐項列出，附原始碼位置 |

安全拒絕只滿足 C／G 的「不寫入」條件，不能算 A 或 B 通過（1.2 原則）。

## 4. 語料與覆蓋率

### 4.1 語料

固定版本，記錄來源與授權，納入 repo 的 fixtures：

- Morph Starter：`src/lib/storefront/__fixtures__/starter-history/` 的歷史版本與目前版本；
- TanStack Start 官方範例：`fixtures/tanstack/start-basic-cloudflare`；
- Astro：`fixtures/astro/cloudflare-astro-blog-starter` 與 `adapter-with-react`（M2 開始後納入）；
- 1.2 B1 與後續驗收案例集的每一個案例；
- 外部社群主題：暫不納入（2026-10-30）。日後納入時先確認授權，只收允許再散布的。

### 4.2 量什麼

對每份語料的每個頁面，記錄 Design 對每個可點選元素上各欄位與操作的判定，按框架統計：

- A、A-code、B、B-partial、C、G、未分類各自的數量（列數字，不換算成百分比，與 1.2 的進度記法一致）；
- 未分類必須是 0（分類完整；不代表支援）；
- G 清單逐項列出原始碼位置，作為下一條規則的排序依據；
- 與上一次結果比較：等級下降的元素逐項列出。

判定取自 Design 本身的分類結果，不另寫一套分析器。報告只記錄 Design 怎麼判定，不證明判定正確；判定是否正確，由有預期答案的驗收案例確認（4.4）。

### 4.3 在 CI 的角色（2026-10-30 確認：先報告）

先產出報告、不擋合併，建立基準。是否把「未分類 = 0」與「沒有未說明的降級」設為必要檢查，另行決定，不在本規格授權範圍內。

### 4.4 判定的正確性

語料統計只說明 Design 判定成什麼。正確性由驗收案例集確認：每個案例都寫明預期答案（每個欄位與操作的等級、A 的寫入目標、B 的完整來源清單、C 的原始碼位置），Design 的判定與預期不符就是失敗。判定正確，再依第 3 節驗收實際行為。

## 5. 規則擴充原則

- 規則做在共用資料流模型（變數、別名、props、spread、多層傳遞、跨元件、純函式），不做在元件名稱或特定寫法上。
- 每條新規則都要附正向案例（升級為 A 或 B）和反向案例（必須維持 B／C／G，例如同名但不同來源、條件分支、列表中的不同列）。
- 擴充的順序依序考量：
  1. 安全性：可能寫錯欄位、寫錯實例或弄丟內容的，最優先；
  2. 既定承諾：ROADMAP 已列為驗收條件或已確認缺口的（例如 1.2 的正式案例、區塊內同名轉傳、C4b）；
  3. 主要流程：首頁、Starter 主要區塊等作者最常編輯的位置；
  4. 語料中的出現頻率。

  只出現在單一寫法、又不涉及前三項的情況，留在 G，直到語料證明它常見。
- 不承諾自動理解任意轉換。不能唯一反推的值，終點就是 B，不是 A。

## 6. 交付順序（建議）

| 步驟 | 內容 | 完成時成立的承諾 |
|---|---|---|
| S1 | 等級模型與分類輸出（不改介面），語料基準報告 | 每個欄位與操作都有等級；缺口有清單 |
| S2 | Inspector 的 B／C／G 呈現：來源清單、原始欄位編輯、跳到原始碼 | 狀態與替代入口已交付 |
| S3 | 依第 5 節的順序逐步擴充 A：已確認缺口優先（區塊內同名轉傳 `<Heading title={title} />`、C4b 跨區塊覆蓋、多層傳遞） | A 的範圍隨證據擴大 |

S2 完成時只標為「狀態與替代入口已交付」：每個欄位與操作都有明確狀態與可操作的入口。G 與 B-partial 仍是能力缺口，不因此算支援。S3 是持續的工作。與 1.5 里程碑的關係：S1、S2 補上 1.2 已確認的缺口「Design 還沒有三種狀態」；S3 對應 M4。Astro 與其他框架各自在 M2、M6 套用同一份等級模型與驗收。

## 7. 不在範圍內

- 保證任意程式都能執行（執行契約之外的依賴、環境、作者程式錯誤）；
- 替不可反推的值猜測拆分方式；
- 隱藏字元（stega）作為產品機制（1.2 第 7 條，只用於測試探測）；
- 影子紀錄等執行時來源追蹤：維持研究項目，不列保證。
